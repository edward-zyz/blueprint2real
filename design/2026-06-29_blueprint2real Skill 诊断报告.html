blueprint2real Skill 诊断报告

多 Agent 工单编排器 · 批判性评估(侧重缺点与改进)

评估基准:1 批 11 工单全链路实战 + SKILL.md 47KB / 11 agent 模板 / 4 篇 references 全勘察 2026-06-28
一句话定性:这是一套事故驱动、补丁叠补丁的高仪式化协议。内核(TDD + 物理分离 commit + 单一事实源 + 诚实边界)确实有效;但它把"全自主"的承诺架在了一个极强的隐性假设上——主线 LLM 永不偷懒地亲跑每条命令、永不误判每种失败、永不漏跟踪每条工单。本会话证明这个假设会破(编排者自己就漏跑了一条工单),而它的认知负荷与维护债,已逼近甚至超过它要防范的退化风险本身。

一、实际工作流程(本会话真实形态)

文档画的是 6 阶段流水线;实跑下来的真实形态是——主线作为串行编排器,对每条工单循环:

promote.mjs(脚本)
 → 派 spec-drafter (merge_2b 合并 spec+plan)      [Agent 往返 1]
 → 主线亲跑 tbd grep + validate + deps 校验
 → 派 spec-plan-reviewer (2c 独立评审)             [Agent 往返 2]
 → start.mjs(脚本,需手动注入 B2R_HOME)
 → 派 implementor (TDD 红→绿)                      [Agent 往返 3]
 → 主线亲跑 targeted + 收敛 regression
 → [L3] 派 arch-security-reviewer → 主线写 4-arch   [Agent 往返 4]
 → 派 handoff-committer → 主线写 pipeline-status     [Agent 往返 5]
 → 主线亲跑 verify:handoff

实测数据:单条工单 5–6 次 Agent 往返 + ~8 次主线脚本校验;11 工单 ≈ 50+ 次 sub-agent 派发(每次 fresh context 重读 spec/plan/模板);连纯文档 / spike 工单(只产一个 .md)也走全套重流程。第一个发现:流程对"产物复杂度"不敏感,文档工单和跨模块重构付一样的仪式开销。

二、优点(客观)

  • commit 物理分离 + TDD 强制是真有效的——每条工单 impl/handoff commit 干净分离可独立 revert;红 gate 真实失败证据挡住"先写实现"退化(本会话 11 条都有)。
  • 状态机单一事实源 + 脚本兜底——validate-state 多次在手滑时挡住;BOARD 由 render 生成不可手改,审计链完整。
  • 诚实边界做得好(最值得肯定)——本会话 ig→linkedArr defer、7r→生产 backfill defer、97→真人签字、组级 E2E→env-blocked,全部如实标注未伪造绿。
  • Manager Override 不静默循环——retry-once 后强制升级到人,机制健全。

三、缺点与改进点(重点)

3.1 「全自主」是个幻觉——关键节点结构性回落人工

所有需要价值判断的地方全部硬性回落人工 AskUserQuestion:coalesce 合并(O28)、ui_paths_stale / ui_intent(O15/O27)、Manager Override(attempt>2 / 自报阻塞 / Gate8 fail)。

本会话实证:97 安全签字 + 组级 E2E 收口两次 AskUserQuestion 都是流程硬卡点,没人就推不下去。这不是"偶尔需要人",是设计上把所有不确定性外包给人。
改进:诚实重定位为 human-in-the-loop 编排器,显著位置列全"必停问人"清单;无人值守模式明确声明哪些工单类型根本不能跑。
3.2 「自报不算数」原则被自己系统性侵蚀

立身核心原则,却被多处打折:L1 self-review 既当运动员又当裁判(L1 跳过独立 reviewer 由 drafter 自评);「证据非空即过」只校验红 gate 输出非空、不校验真的是失败,塞任意非空串即可骗过;散文判据仍在(reviewer"总判定"、deps"依赖合理"本质解析自然语言)。

本会话实证:97(L1)的 receipt 根本没出 l1_self_review_verdict 字段,是主线亲核兜底才发现。
改进:取消 L1 自评旁路或停止宣称它"有 gate";红 gate 应校验失败结构(退出码 / FAIL 关键字)而非仅非空。
3.3 委派的「底层 skill」在真实环境根本没生效

模板大讲调 brainstorming / writing-plans / test-driven-development……

本会话实证:绝大多数 sub-agent 返回的 skills_used 是 []——这些 skill 在执行环境"未注册",只能"按其纪律手动执行"。整个 v2 "skill-delegating" 架构在本环境是空中楼阁,模板里"第一步调 X skill"是 dead instruction,全靠 prompt 复述纪律硬撑——这是模板臃肿根因之一。
改进:模板先探测 skill 可用性,不可用走精简内联纪律,而非每个模板背两套逻辑。
3.4 环境健壮性差(硬证据)
坑证据性质
B2R_HOME 硬编码他机路径start/render/verify 的 alias 兜底是 /Users/zhangyingze/Documents/...,本机不存在,每条命令都要手动 export分发缺陷,memory 已记录仍未根治
validate-state 鸡生蛋Done 工单要 5-handoff.json,但该 receipt 要 handoff hash,hash 又要 commit 后才有 → 每个 handoff 都要绕"render→commit→写receipt→复跑"圈状态机自指,每单复发
lint:redlines 空跑项目没配红线 → WARN → Stage 4"红线 gate"形同虚设却显示通过gate 形式主义
改进:B2R_HOME 应在 init 写项目本地配置而非硬编码他机绝对路径(最该立刻修);5-handoff 存在性校验应豁免"hash 待生成"中间态。
3.5 大量声称能力有结构性高门槛,实践中跑不起来

本会话未触发的能力不是巧合,是结构性门槛:UI 线(ui-designer/design-reviewer)依赖外部 designSkill + 活服务 + 浏览器截图;E2E 线模板自己坦白 playwright"恒 2 passed+3 skipped、缺浏览器/secrets 即 env-blocked";L0 direct-fix 判据窄到真实命中率极低;roadmap-planner 在工单预 mint 用法下被整个旁路。

结论:只有 L1–L3 后端工单循环是真能无人值守跑的核心;其余几支是高环境门槛、需人工+活服务配合的"可选枝"。文档却把它们写成平级能力,给"开箱即用"错觉。
改进:文档分层标注每条线的"环境前置 + 自给程度"。
3.6 主线编排器是未设防的单点失败(最尖锐)

整套"脚本兜底"全建立在主线每次都亲跑、且永不漏跟踪上,而主线没有任何强制约束,纯靠纪律。

本会话铁证:编排者列了 10 工单计划、做到 z3 就以为收官,实际漏了 pi——是 handoff-committer 在报告里点出"组里 pi 仍 Planned"才发现。这正是该 skill 声称要根治的退化("以为做完了")在主线侧的同构复发:它给 sub-agent 设了天罗地网的 gate,却忘了给编排者自己设 gate。
改进:加"批次完整性"硬校验——每次 handoff 后强制比对"计划 N 条 vs 已 Done M 条",而非靠主线心算。
3.7 三套编号 + 双源契约 = 认知过载与实质冲突

协议层有三套互不对齐的编号:state 用不变量号(1-7/D4/D5)、quality-gates 用 Stage+节点、pipeline-flow 用 Gate(G2-G8)。同一判定点三个名字,且已出现实质冲突:downgrade 回流点在 quality-gates 写"Gate 4"、在 pipeline-flow 写"回 Gate 6"。加上双源契约(.mjs 与 .md 双写校验规则必漂移)、Markdown 当数据库(表头列序/"≤2行/≥3条"当 hard schema)、receipt 数百字段 + 条件必填地狱(本会话多个 2b receipt 字段漂移成非标准形状)。

改进:编号统一一套;校验规则单源(脚本为准、文档自动生成);receipt 必填字段集中校验表 + 宽松解析。
3.8 成本/效率:固定开销对小工单严重倒挂

文档 / spike 工单(rk/ig/97)产物就一个 .md,却付了和跨模块重构(ex)一样的 5–6 次 Agent 往返 + 全套 review/regression。O28 的 coalesce 合并本为治这个,但只在 Stage 1 同批线性链触发且要问人——本会话工单预 mint,该优化整个没生效。

本会话实证:triage 3 次误判 L1(ci/qh/97 的 reasons 全是自相矛盾的"单文件却涉及3文件"),主线手动升档 2 次。triage 质量低导致路由失准。
改进:小产物工单(纯文档/spike)走专门轻量路径;修 triage level 判据(reasons 自相矛盾说明判定 prompt 有 bug)。

四、优先级改进清单

P0 — 立即(低成本高收益)

  • 修 B2R_HOME 硬编码他机路径:init 时写项目本地配置。最低级的分发 bug,每条命令都被它绊。
  • 修 triage level 判据:"单文件却涉及3文件"自相矛盾说明判定逻辑坏了,本会话 3/3 误判。
  • 加批次完整性闸:handoff 后强制比对"计划数 vs Done 数",堵主线漏跟踪(漏 pi 的坑)。

P1 — 结构性

  • 诚实重定位为 human-in-the-loop,列全"必停问人"清单,停止"全自主"宣称。
  • 修 validate-state 鸡生蛋(豁免 handoff hash 中间态)。
  • 统一三套编号 + 契约单源,消除 Gate4/Gate6 实质冲突。
  • 红 gate 校验失败结构而非仅"非空"。

P2 — 架构债

  • 底层 skill 委派做可用性探测,不可用时精简模板。
  • 小产物工单(文档/spike)轻量路径,不走全套仪式。
  • receipt schema 瘦身 + 宽松解析(数百字段+条件必填是 sub-agent 最高频失败点)。

五、收尾判断

blueprint2real 的内核是好的,本会话也确实产出 11 条干净可回滚、状态完整的工单。但它把好内核包裹在过度仪式化的外壳里:三套编号、数百字段 receipt、事故驱动的 gate 膨胀、对主线纪律和人工值守的隐性全量依赖。

最尖锐的一条:它给 sub-agent 设了天罗地网的 gate,却忘了给编排者自己设 gate——而本会话恰恰是编排者漏跑了一条工单。一个声称根治"以为做完了"的系统,在它最信任的主线节点上复发了同一种退化。这是它最该照镜子的地方。
